# TRM reorientation: email + decision_pipeline / new modules (2026-10-28)

The user no longer uses Google Chat; they send and read email. TRM work moves from gchat
to email (MJML) plus cross-module search on non-gchat modules. Branch
`feat/trm-learned-search` (from 3.3.3). Research code under `research/trm/email/`
(gitignored).

## Real labelled data

Every email rendered by `compose_dynamic_email` since 2.13.0 embeds its EmailSpec in an
HTML comment (`gmail.email_templates.embed_email_spec`), so the user's Sent folder is a
labelled corpus: which block type every piece of content went into.

- **46 unique compose emails, 494 items** (431 with text after dropping Divider/empty):
  Sentry Triage, Issue Hygiene, Scout Brief, Shelf Notes, Hearth haunt, a few one-offs.
  64 of 93 non-reply sent emails since Aug 29 are compose-built.
- **Harvest route.** Local credential files are encrypted with per-user keys that live
  only in an authenticated server session, so scripts can't read Gmail directly (by
  design; not bypassed). Instead: `riversunlimited-local` → `execute` →
  `manage_email_templates` save(message_id, `trm_tmp_*`) [→ get] → delete. Full tool
  responses land in Qdrant `mcp_tool_responses` (compressed or `response_data`), read
  locally. `search_gmail_messages` caps `page_size` at 100 with no paging token → split
  by date window. Batches over ~40 messages hit the 5-min MCP idle timeout (the server
  keeps going; check for leftover `trm_tmp_*` templates — none left).

## 1. Item → block placement (the model's real touchpoint in email)

Email builds don't use learned search. The model reaches email only through
`assign_items_to_components` (compose orphan rescue), which scores items against
**content prototypes** (mean embeddings carried on checkpoint metadata); the model heads
were measured at chance. The email *pool* head is nearly useless here: Hero, Text,
Button and Image all map to the one `content` pool.

`research/trm/email/train_assign.py`: per-item features = MiniLM(item text) + position
in the email + text shape (length, links, markup). Field keys are deliberately not
features (harvested params carry block-specific defaults like `title_size`). Small MLP,
class-balanced, then max-score matching against the email's block demands.
**Leave-one-family-out** (10 families) so templates can't be memorized.

| method (431 real items) | accuracy |
|---|---|
| **learned + demands** (MLP 64) | **90.0%** |
| learned + demands (linear) | 87.9% |
| learned, text only | 75.6–78.2% |
| learned, position/shape only | 80.0% |
| majority (TextBlock) | 59.4% |
| production prototypes + demands | 44.5% |

Per block (learned, all features): Text 245/256, Footer 43/44, Header 24/27, Hero 35/44,
Image 27/41, Button 14/18. Text supplies images/buttons; position supplies
header/footer.

Caveat: in orphan rescue an item's position in the email may be unknown — text-only
(≈76–78%) is the conservative estimate, still +32 pts over prototypes.

### Shipped in code (not yet deployed)

`gchat/card_builder/slot_assignment.py`: `score_items_for_components` now uses a learned
**placement head** when the domain checkpoint carries one (`placement_head`: MLP over
MiniLM(item text) + `placement_shape_features`, position-free because orphan items have
no position), else falls back to content prototypes as before. Blocks the head never saw
(Divider/Spacer) are scored out instead of abandoning the email. Image items use their
alt text / URL (`placement_item_text`). Tests: `tests/module/test_placement_head.py`.

`research/trm/email/build_placement_head.py` trains the head on all real items through
those production feature functions and writes the email checkpoint + head
(`research/trm/email/email_unified_with_placement.pt`). Held-out-family accuracy through
the production path: **78.2%** (position-free) vs prototypes 44.5%. On the production
`assign_items_to_components` path over all 443 real content items: current checkpoint
56.0%, with head 100% (in-sample; the 78.2% is the honest number).

**To deploy:** publish that checkpoint under the `email` key of the model artifact store
(`MODEL_ARTIFACT_URI`). Until then production behaviour is unchanged.

## 2. Layout from intent — parked

`layout_eval.py`: subject + preheader → block sequence, leave-one-family-out. kNN from
other families: Jaccard 0.75, exact 22%; global most-common layout: 0.72 / 16%; even the
same family's mode: 0.92 / 20% (report layouts vary run to run around one skeleton).
Nothing to learn from 10 families; saved templates already cover the reuse case.

## 4. Received (designed) emails — hurt as training data

`parse_inbox.py`: 34 promotional emails (HTML via template round-trip) → 1,088 items
labelled by DOM structure (rendered `<img>`, button-styled links, first large heading in
the top third, small type in the bottom band, hidden/MSO content skipped). Added to
training (never evaluated): **90.0% → 76%**, at any weight from 1.0 down to 0.1 (0.0
reproduces 90.0%). Their structure-derived labels conflict with how the user's emails
are built; images and buttons collapse. Not used.

## Bugs found

- **`manage_email_templates` `get` fails on ~15% of received emails** (6/40):
  `Error serializing to JSON: UnicodeEncodeError … surrogates not allowed` at position
  ~2000 — the saved HTML carries lone surrogates (likely an emoji split by decoding or
  truncation). Needs a repro with a failing message id; not fixed.

## 3. Module search without gchat — no gain over rrf; more modules don't help

Groups regenerated with the fixed retrieval (decision_pipeline v2: GT in pool 85% vs
~75% before; anthropic.types 29%, langfuse.api 40% — many same-named classes).
`generate_module_groups.py` now retries/skips on cloud-Qdrant gRPC deadlines.
`transfer_eval.py --wrapper <MODULES key>` evaluates any wrapped module. Unseen test
modules, n=150 queries (openai.types yields 92):

| training (no gchat) | qdrant_client.models Top-1 (s7/s42) | openai.types Top-1 (s7/s42) |
|---|---|---|
| rrf (model-free) | 23.3% | 39.1% |
| dp v2 + mcp.types | 22.0 / 22.7% | 34.8 / 35.9% |
| + anthropic.types + langfuse.api | 22.0 / 20.7% | 33.7 / 37.0% |
| gchat live + dp (`live_md_s7`, earlier) | 23.3% | 34.8% |

Learned top-5 / recall@10 are 1–2 pts above rrf, Top-1 0–5 pts below. Doubling the
training modules changes nothing. On an unseen module the reranker's 17 features carry
no more than ColBERT's own ranking, so **more training modules is not the lever**. The
lever is the input: class points' `inputs`/`relationships` vectors embed only the symbol
name and `content` is empty, so the docstring reaches retrieval only through ColBERT.
Next step there is an indexing change (a dense docstring vector on class points), not
more training data.
