# FastMCP 3.4.7 → 4.0.1 migration plan (issue #53)

Prepared 2026-09-02 against FastMCP 4.0.1 (GA 2026-09-01, MCP Python SDK 2.1.1, protocol 2026-07-28).
Every claim below was checked against a scratch install of 4.0.1 and a full-project install in a throwaway worktree, not just the release notes.

## Verdict

Proceed. The Aug-7 read ("stay on 3.x") rested on three assumptions that turned out weaker than feared:

1. **Import churn is tiny.** Of 64 fastmcp/mcp import paths this repo uses, 62 resolve unchanged on 4.0.1. The two that moved are both tasks modules. Dependency resolution is clean (246 packages, no conflicts).
2. **Era negotiation is per connection.** A 4.0 server serves handshake-era clients (sessions, `ctx.set_state`, `ctx.elicit`) and 2026-07-28 clients from one deployment. Nothing forces existing connectors onto the sessionless protocol. Only `ctx.sample` disappears for everyone.
3. **Caller-model sampling survives on the modern protocol**, in request form: a tool returns `InputRequiredResult` carrying a `CreateMessageRequest`, the client's `sampling_handler` answers, and the tool re-runs with `ctx.input_responses`. That keeps the evals harness's "swap the model, keep the server" trick possible, though a simpler path exists (below).

The real work is one thing: re-homing the server-side sampling runtime that FastMCP 3 provided and this server is built on. Everything else is a day of mechanical edits.

Suggested shape: one feature branch, three reviewable PRs, shipped as **Release 3.0.0** (the framework major changes protocol defaults and moves all sampling cost server-side, which users will notice). Modern-protocol readiness follows in later minors.

## Behavior changes that tests will not catch

1. **All sampling cost moves server-side.** On 3.4.7 a client that advertised sampling fulfilled `ctx.sample` with its own model; on 4.0 there is no server→client sampling on any era. Every draft-variation, DSL-recovery, and email pre-validation call now bills the server's LiteLLM/Anthropic key. `SAMPLING_MONTHLY_BUDGET_USD` becomes load-bearing and per-user provider config (`/api/sampling-config`) becomes the way users pay their own way.
2. **Modern-protocol clients are stateless per request.** Each request is a fresh connection, so `ctx.session_id` is a new UUID every call and `ctx.set_state`, the `auth/context.py` session store, disabled-tool state, and `SessionToolFilteringMiddleware` do not carry over. There is no server-side setting to refuse the modern era (checked `fastmcp/settings.py`), so readiness is code, not config (Phase 3). Handshake-era clients are unaffected.
3. **`send_notification(ToolListChangedNotification())`** only rides the in-flight request's stream on sessionless connections; unrelated notifications are dropped. Legacy clients still receive them.
4. **Elicitation raises on modern connections.** Both Gmail sites already catch generic exceptions and return `elicitationRequired=True` with the recipients listed, so modern clients degrade to "confirm and resend" instead of crashing. Acceptable until the guard-tool port.
5. **Middleware sees every inbound message.** `auth/middleware.py:180` `on_request` creates/pops a session entry per request; harmless, but guard on `context.method` so cancelled/unroutable messages do not churn the store.
6. **Freshly minted JWTs may differ**, forcing a one-time re-authorization of Claude.ai/Desktop connectors. Verify on the local :8002 server with Claude Desktop before release; the Google app's "Testing" 7-day refresh expiry makes forced re-auth annoying.
7. **Telemetry is on by default** (opentelemetry-api is now a hard dependency). Set `FASTMCP_TELEMETRY_MODE` deliberately and confirm it coexists with the Langfuse OTEL phase spans.

## Bug found while reading the seam

`SessionAwareSamplingHandler._get_session_sampling_config` (middleware/session_sampling_handler.py:65-110) walks *all* active sessions newest-first and returns the first `SAMPLING_CONFIG` it finds. It never checks the requesting session or user. With two authenticated users online, user B's sampling calls can route through user A's model and API key. The inversion in Phase 1 passes `ctx` into the handler, so resolve only the current session's config there (or fix it on 3.4.7 in Phase 0; it is independent of the upgrade).

## Phases

### Phase 0 — prep on 3.4.7 (½ day, ships any time, no behavior change)

- Delete dead code: `setup_enhanced_sampling_demo_tools` and its ~10 `ctx.sample` demo tools, `EnhancedSamplingMiddleware.on_startup`, `_create_elicitation_tool`.
- `TaskConfig` import: try `fastmcp.utilities.tasks`, fall back to `fastmcp.server.tasks`. Drop `task=` from the two chat-digest resources (3.4.7 does not need it either).
- Routable-message guard in `auth/middleware.py` `on_request`.
- Fix the cross-user sampling-config lookup.

### Phase 1 — PR A: sampling inversion (2–3 days, the substance)

- **Vendor** FastMCP 3.4.7's `fastmcp/server/sampling/run.py` + `sampling_tool.py` (984 lines, Apache-2.0, keep the header) as `middleware/sampling_runtime.py`. It already contains everything the server relies on: the tool loop, the synthetic `final_response` tool for `result_type`, validation retries, `SamplingResult`/`SampleStep`, and OTEL spans. Delete `determine_handler_mode` and the wire path; `call_sampling_handler` always calls our handler.
- **Public API** mirrors the old context methods so call sites change one line: `await sample(ctx, messages, *, system_prompt, temperature, max_tokens, model_preferences, tools, result_type)` and `sample_step(...)`. Only two live callers: `SamplingContext.sample` and `send_dynamic_card` draft variations.
- **Handler registry**: keep `create_sampling_handler(settings)`; store the result on the server instance instead of the removed constructor kwargs. Pass `ctx.request_context` as the handler's third argument (what 3.4.7 passed; our handlers use it only for Langfuse metadata).
- **snake_case** the LiteLLM handler and the `CreateMessageRequestParams` we now construct ourselves; drop the client-side `sampling_capabilities` workaround noted in the evals memory.
- **Per-user routing** stays in `SessionAwareSamplingHandler`, now keyed to the current session (bug fix above).
- Tests: `tests/test_sampling_tools.py`, `tests/test_sampling_middleware_unit.py`, `tests/module/test_argument_recovery.py` mock `SamplingContext.sample` and mostly survive; anything that patched `fastmcp_context.sample` moves to the runtime.

### Phase 2 — PR B: mechanical sweep, tasks, deps, harness (1 day)

- pyproject: `fastmcp[anthropic,tasks,code-mode,apps]>=4.0.1`, `pydantic>=2.12`, `fastapi>=0.133`, add `httpx2`; `uv lock`; bump `pyproject.toml` and `uv.lock` versions together; CI pytest step gets `FASTMCP_MCP_CAMELCASE_COMPAT=false`.
- server.py: remove the two sampling kwargs; `mcp.add_extension(TasksExtension())` (default backend `memory://` is right for the single-process Docker and Glama containers; `FASTMCP_DOCKET_URL=redis://…` only when running replicas); log `ctx.request_context.protocol_version` once per request in the auth middleware so we learn which era Claude.ai and Claude Desktop negotiate.
- App-only tool filtering for non-UI clients (root cause D).
- httpx2 in the four transport-factory sites; tasks client import in the test helper; pin `Client(mode="legacy")` in `tests/client/test_gmail_elicitation_system.py` and the reply/forward tests until Phase 3.
- **Evals harness**: replace the client-side `sampling_handler` with a per-model `POST /api/sampling-config` (model, api_key, api_base) against the eval user's authenticated session before each run and `action: "clear"` after. That endpoint rejects shared-API-key sessions, so the harness needs the eval user's OAuth session, which is already required for Gmail/Chat scenarios. Usage and cost now happen in the server process: read them from Langfuse generations by trace/session id (the LiteLLM Langfuse callback and `_SamplingTraceContext` already tag them) instead of the in-process `SamplingUsageCollector`. The judge stays local.
- Docs touched by sampling/elicitation wording: docs/GMAIL_DRAFT_APP.md, docs/payment_model_architecture.md, documentation/config/CONFIGURATION_GUIDE.md, documentation/api-reference/gmail/README.md. Regenerate plugin skills and run `--check`.

### Phase 3 — modern-protocol readiness and new capabilities (3–5 days across later minors)

1. **`UserSession` for per-user state.** v4 stores a per-user bucket keyed by the authenticated principal, injected like `ctx: Context`. It replaces the email→session walking in `find_session_id_by_email`, `restore_session_tool_state_by_email`, and the per-user sampling config lookup, and it works identically for handshake and modern clients. Migrate `SAMPLING_CONFIG`, disabled tools, privacy mode, and payment receipts first. For shared-API-key sessions (no principal) use `SessionId` + `SessionProvider`, or derive a stable key from the key hash. Add `FastMCP(session_state_store=<Redis AsyncKeyValue>)` so `ctx.set_state` survives replicas.
2. **Gmail confirmation as a guard tool.** Branch on `ctx.request_context.protocol_version in MODERN_PROTOCOL_VERSIONS` (`mcp_types.version`): legacy keeps `ctx.elicit`; modern returns `InputRequiredResult(input_requests={"confirm": ElicitRequest(...)})` and on the next round reads `ctx.input_responses["confirm"].action` / `.content`. The tool's return annotation becomes `SendGmailMessageResponse | InputRequiredResult`. Configure `request_state_security` keys only if replicas share state.
3. **Cache hints** (`cache_ttl`, `cache_scope="private"`) on list-shaped tools and resources: service lists, `tags`, `get_schema`, dashboard cards. Zero code beyond the decorator kwargs; caching clients stop re-fetching.
4. **Argument completion** via `@mcp.completion` for `chat://digest/space/{space_id}` and the Gmail/Chat prompt arguments.
5. **Tool-level `auth=` checks** (`require_scopes`, `require_roles`) on `manage_tools`, template management, and payment admin endpoints instead of ad-hoc admin-key checks.
6. Optional: move the x402 payment handshake to a `ServerExtension` (`add_extension`, SEP-2133) so it advertises a capability instead of living in middleware; feed the `mcp.protocol.version` span attribute into Langfuse.

## Implementation status (2026-09-02)

Branch `feat/fastmcp-v4`. Phases 0, 1 and 2 are implemented; Phase 3 is not started, apart from the two elicitation items below.

- **Phase 0**: dead sampling demo tools and the never-invoked `on_startup` transform deleted; `task=` dropped from the chat-digest resources and the unused `TaskConfig` import removed; auth `on_request` guarded to session-scoped methods; per-user sampling config now resolves only the current session.
- **Phase 1**: `middleware/sampling_runtime.py` vendors the 3.4.7 loop (tool execution, `final_response` structured output, validation retries, OTEL spans) with the wire path removed. `SamplingContext.sample` and `send_dynamic_card` call it; `server.py` registers the handler with `set_sampling_handler`. LiteLLM handler and tests moved to snake_case. New unit tests in `tests/test_sampling_runtime.py`.
- **Phase 2**: `fastmcp[…]>=4.0.1`, `pydantic>=2.12`, `fastapi>=0.133`, `httpx2`, version 3.0.0; `TasksExtension` registered; `AppVisibilityMiddleware` hides app-only tools for non-UI clients; protocol-version log line; httpx2 in the four transport factories; client suite pinned to `mode="legacy"` with a `MessageHandler`-based tool refresh; CI runs with `FASTMCP_MCP_CAMELCASE_COMPAT=false`; plugin skills regenerated; docs and `.env.example` updated.
- **Evals harness**: instead of `/api/sampling-config` (which rejects the API-key session the harness uses), the server gained an opt-in per-request override: `X-Sampling-Model` / `X-Sampling-Api-Base` / `X-Sampling-Api-Key` headers, honored only when `SAMPLING_ALLOW_HEADER_OVERRIDE=true`. Per-item token usage now accrues server-side; reading it back from Langfuse is deferred.
- **Found during verification — result key stripping.** FastMCP 4 serializes a tool's return value through its return annotation, so a TypedDict-typed result loses any key the TypedDict does not declare (FastMCP 3 passed the dict through untouched). `send_gmail_message` / `forward_gmail_message` emitted `messageId`, `threadId`, `contentType`, `templateApplied`, `templateName`, `message` that `SendGmailMessageResponse` never declared, and `get_form_response` emitted `message` on `FormResponseDetails`; both TypedDicts now declare them. An import-resolved AST audit of all 152 TypedDict classes found no other production mismatches.
- **Elicitation fallback gate corrected.** The plan assumed both Gmail elicitation sites already degraded cleanly on a modern connection. They did not: FastMCP 4 raises `ToolError("elicitation via server-initiated requests is unavailable on 2026-07-28 connections.")`, and the sites' `is_unsupported_client` predicate matched on "unsupported"/"not available", so a modern client fell into the "client supports elicitation but errored" branch and `gmail_elicitation_fallback` was never applied — an `allow` or `draft` fallback silently did nothing. The predicate (duplicated verbatim in both sites) is now the single `_is_elicitation_unsupported` helper in `gmail/compose.py`, which also recognizes the no-back-channel case. Unit tests in `tests/test_elicitation_fallback.py`.
- **Phase 3 item 2, partial — url-mode elicitation for OAuth.** `tools/elicitation.py` (then `auth/oauth_elicitation.py`) wraps both wire shapes behind one call: handshake connections push `elicitation/create` with `mode: "url"` via `session.elicit_url` and get an answer inside the same call; 2026-07-28 connections get an `InputRequiredResult` carrying the same `ElicitRequest`, and the re-run reads `ctx.input_responses`. `start_google_auth` uses it (return annotation `StartAuthResponse | InputRequiredResult`, which FastMCP strips back to `StartAuthResponse` in the output schema), so the OAuth detour no longer ends the tool call and the user does not have to re-ask afterwards. Gated on the client declaring `elicitation.url`; every other path — form-only client, no session, back-channel error — falls back to today's clickable link, so behavior is unchanged for clients that do not support it. A refused round returns a cancelled response rather than prompting again, so a decline cannot loop. Code Mode is guarded separately: its sandbox calls tools through `ctx.fastmcp.call_tool`, and an `InputRequiredToolResult` carries no content, so a suspend there would reach the sandbox as an empty value and lose the URL — `suppress_elicitation()` wraps `sandbox_provider.run` so nested calls always take the link path. Tests in `tests/test_oauth_url_elicitation.py`. Gmail's send/forward confirmation followed the same day (last entry in this section).
- **`execute` is the unit of background work under Code Mode.** Live verification showed Claude Code negotiates 2026-07-28, so tasks are reachable — but not through `create_gmail_filter`'s own `task=True`: Code Mode's sandbox calls tools in-process via `ctx.fastmcp.call_tool`, which never reaches the tasks extension binding, and `task=True` maps to `mode="optional"`, so the tool quietly runs inline. The block is the only thing that crosses the wire, so `execute` now carries `task=True` (optional mode: a client that negotiated the extension may opt in per call; everything else runs inline as before). `setup_code_mode` registers `TasksExtension` idempotently — FastMCP refuses to serve a task-capable tool without it — so a bare `FastMCP` works and `server.py`'s earlier registration is respected. Found while doing it: a task worker restores the submitting request's HTTP headers and token but not its `initialize` params, so `client_renders_ui()` had no handshake in the worker and defaulted to "render", handing a view spec to a client that could not draw it (the FastMCP in-memory client auto-opts into tasks, which is how the code-mode test caught it). `tools/client_capabilities.py` now identifies a worker-leg client from the restored `User-Agent` against the same allowlist and resolves "unknown" to text-only there; the non-task no-handshake default is unchanged. The `[ui-gating]` log line now reports the identity's source so a real client's UA can be added to `DRAFT_PREVIEW_UI_CLIENTS`. Tests in `tests/test_ui_gating.py` (worker section) and `tests/test_code_mode.py`.
- **Background tasks, checked against the guide's section.** Done: `fastmcp[tasks]` extra, `mcp.add_extension(TasksExtension())` registered at import time (before the lifespan), `task=True` unchanged on `send_dynamic_card` and `create_gmail_filter`, `task=` removed from the two resources (v4 raises `TypeError` there), no remaining `fastmcp.server.tasks` imports, no `call_tool(task=True)` callers, `FASTMCP_DOCKET_URL` documented. Added after re-reading the guide: `FASTMCP_TASKS_ENCRYPTION_KEY` documented (snapshots hold the caller's token and headers and are plaintext without it; required on Redis), the evals client now imports `fastmcp_tasks` so modern connections negotiate real tasks, and the per-request sampling override reads `get_http_headers()` rather than `get_http_request()` because workers restore headers but never a live request. The client test suite stays on `mode="legacy"`, where tasks are never negotiated, by design.

- **Per-session client record, moved to the first request.** `credentials/session_tool_states.json` carries a `client` record per session (handshake `clientInfo`, negotiated era, elicitation modes, tasks, `User-Agent`, and the CIMD `oauth_client_name` such as "Claude Code"). It was captured in `on_call_tool`, so every session that only listed tools — Claude Code's connect-and-idle pattern — persisted `client: null`. Verified with a FastMCP 4 client over HTTP: a 2026-07-28 client sends no `initialize` at all (first message is `server/discover`), carries `clientInfo` in each request's `_meta`, and the SDK synthesizes `session.client_params` from it, so `AuthMiddleware.on_request` now records on the first request of any kind; `on_initialize` covers handshake-era clients (their `client_params` is committed only after the initialize chain returns, so it reads the request params); `on_call_tool` stays as a fallback. The same probe confirmed the behavior-change note above: with no `Mcp-Session-Id`, `ctx.session_id` is a fresh UUID per request, so every request is its own session until Phase 3's `UserSession` keys state by principal. Two consequences shaped the capture: (a) the record is stored on the live session and never persisted from the record path — `persist_session_tool_states` rewrites the file from the live store, so the first write of a fresh process replaces the previous process's entries, and writing from `server/discover` wiped the predecessor that the tools/list restore looks up by email (every session then showed `user_email: null` and inherited nothing); (b) a session known only by its client is not written, or the file would gain one identity-less line per `server/discover`/`resources/list`. The record reaches disk with the session's own persist (restore, enable/disable, minimal startup). Also observed: `SessionToolFilteringMiddleware.on_call_tool` checks the *calling* request's session, which under 2026-07-28 is always fresh, so a session-scoped disable no longer blocks a direct call from a modern client — another Phase 3 item.

- **OAuth elicitation for Claude Code, under Code Mode (2026-09-02, later the same day).** Claude Code 2.1.258 declares exactly `{roots: {listChanged: true}, elicitation: {}}` (read out of the installed binary; its docs say form and URL dialogs appear with no configuration).
